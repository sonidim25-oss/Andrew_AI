# План устранения задержек обработки сообщений

## Главная находка: узкое место в обработке сообщений

После просмотра `dispatch.py`, `main.py`, `controller.py` и `telegram.py` выявлена конкретная архитектурная проблема.

Сейчас основной цикл выполняет операции последовательно:

1. Обработка входящих сообщений.
2. Проверка расписания.
3. Обработка очереди.
4. Автономная работа Andrew / Letta.

Отдельные потоки для получения Telegram-команд и отправки ответов уже существуют. Это правильно.

Но обработка обычных сообщений, очереди и автономных задач всё ещё может блокировать основной цикл. Кроме того, отправка ответов идёт через один последовательный поток.

Например, если Andrew выполняет долгую операцию, обычное сообщение может ждать завершения предыдущей работы. А если Telegram зависает при отправке, следующие ответы задерживаются.

## Рекомендуемые изменения

| Приоритет | Изменение | Ожидаемый эффект |
| --- | --- | --- |
| P0 | Добавить измерение времени на каждом этапе: получение, очередь, обработка, отправка | Найти реальный источник задержек |
| P0 | Отделить системные команды от автономной очереди полностью | `/status` и `/budget` не ждут модель |
| P0 | Разделить отправку срочных системных ответов и обычных сообщений | Системные ответы не ждут длинные сообщения |
| P1 | Перенести длительные модельные операции в отдельный worker | Andrew может работать, не блокируя обработку новых сообщений |
| P1 | Ввести короткие сетевые таймауты для интерактивных операций | Быстрее обнаруживать зависания |
| P1 | Добавить `/health` с диагностикой очередей и времени ответа | Видеть, что именно тормозит |
| P2 | Сделать прямые команды Gmail для простых проверок | Не вызывать модель без необходимости |


## Ход реализации

Первый этап P0 реализован в исходниках: добавлены ограниченные по памяти
метрики получения, ожидания во входящей и исходящей очередях, обработки команд
и обычных сообщений, расписания, автономной работы, отправки Telegram,
дневника и резервного копирования. Метрики доступны через
`dispatch.metrics.snapshot()`; `/health` относится к следующему этапу.

Возраст очереди вычисляется по UTC и явно отличается от длительности операции,
измеряемой монотонными часами текущего процесса. Старые исходящие записи без
времени постановки сохраняют неизвестный возраст. Тексты и секреты не собираются. Внутренне перехваченные ошибки также учитываются;
сохраняются только фиксированные категории ошибок, а не объекты исключений.

Уточнение по исследованию: системные команды уже обрабатываются отдельно от
модели. Общая очередь отправки по-прежнему может задерживать их ответы.
Первый этап не меняет порядок обработки, сетевые таймауты или политику повторов.

Реализация и проверки: [MESSAGE_LATENCY_IMPLEMENTATION.md](docs/MESSAGE_LATENCY_IMPLEMENTATION.md).
Следующие этапы: удержание неопределённых отправок и независимая системная
доставка, затем единый модельный worker, короткие интерактивные таймауты,
`/health` и прямые проверки Gmail. После отдельного разрешения владельца первый
этап установлен на production 2026-10-16 в 23:08 UTC; лимит Letta — 6000 токенов.
