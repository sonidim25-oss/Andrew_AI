# План устранения задержек обработки сообщений

## Главная находка: узкое место в обработке сообщений

После просмотра `dispatch.py`, `main.py`, `controller.py` и `telegram.py` выявлена конкретная архитектурная проблема.

Сейчас основной цикл выполняет операции последовательно:

1. Обработка входящих сообщений.
2. Проверка расписания.
3. Обработка очереди.
4. Автономная работа Andrew / Letta.

Отдельные потоки для получения Telegram-команд и отправки ответов уже существуют. Это правильно.

Но обработка обычных сообщений, очереди и автономных задач всё ещё может блокировать основной цикл. Кроме того, отправка ответов идёт через один последовательный поток.

Например, если Andrew выполняет долгую операцию, обычное сообщение может ждать завершения предыдущей работы. А если Telegram зависает при отправке, следующие ответы задерживаются.

## Рекомендуемые изменения

| Приоритет | Изменение | Ожидаемый эффект |
| --- | --- | --- |
| P0 | Добавить измерение времени на каждом этапе: получение, очередь, обработка, отправка | Найти реальный источник задержек |
| P0 | Отделить системные команды от автономной очереди полностью | `/status` и `/budget` не ждут модель |
| P0 | Разделить отправку срочных системных ответов и обычных сообщений | Системные ответы не ждут длинные сообщения |
| P1 | Перенести длительные модельные операции в отдельный worker | Andrew может работать, не блокируя обработку новых сообщений |
| P1 | Ввести короткие сетевые таймауты для интерактивных операций | Быстрее обнаруживать зависания |
| P1 | Добавить `/health` с диагностикой очередей и времени ответа | Видеть, что именно тормозит |
| P2 | Сделать прямые команды Gmail для простых проверок | Не вызывать модель без необходимости |


## Ход реализации

Первый этап P0 — измерения задержек — установлен на production 2026-10-16
в 23:08 UTC из `b5708ac` (включает `e4f88e5`). Лимит Letta установлен в 6000
токенов. Метрики доступны через `dispatch.metrics.snapshot()`; `/health` пока нет.

Второй этап P0 реализован в исходниках:

- Системные ответы используют отдельную постоянную очередь и отдельный поток
  отправки. Они могут обогнать обычный ответ, который ждёт Telegram.
- Для каждой очереди допускается один активный отправщик. Получение права
  отправки, завершение и освобождение защищены транзакциями и токеном владения.
- Неподтверждённые попытки удерживаются после ошибки или перезапуска.
  Подтверждённые части не отправляются повторно; точно не отправленные части
  могут продолжить доставку. Полностью подтверждённые ответы завершаются локально.
- Явный повтор дневника по команде владельца сохранён. Автоматического повтора
  неопределённых исходящих сообщений нет; нового `/replay` для исходящих не добавлено.
- При остановке база и история остаются открыты, пока отправщик ещё работает.

Системные команды уже обрабатывались отдельно от модели; новый этап устраняет
ожидание их ответов в общей очереди отправки. Получение обычных сообщений,
`flush_queued()` и автономная работа пока остаются последовательными.

Проект: [MESSAGE_LATENCY_DESIGN.md](docs/MESSAGE_LATENCY_DESIGN.md).
Реализация второго этапа и проверки:
[MESSAGE_DELIVERY_IMPLEMENTATION.md](docs/MESSAGE_DELIVERY_IMPLEMENTATION.md).

Второй этап ещё не развёрнут: в этой работе production не менялся. Манифест
намеренно не обновлялся. При подготовке установки потребуется совместимый откат:
старый отправщик не учитывает новый статус удержания и не должен запускаться
над неопределёнными отправками, созданными новой версией.

Следующие этапы P1: один модельный worker, короткие сетевые таймауты для
интерактивных операций и `/health`. Затем P2 — прямые проверки Gmail без модели.
Модельные вызовы, wake и replay в ходе этой работы не запускались.

Проверки второго этапа: 285 основных тестов — 283 прошли, 2 необязательных
пропущены. Из 58 скриптовых тестов 57 прошли; единственный упавший тест —
контроль установочного манифеста (пять изменённых модулей). Ревью не нашло
блокирующих дефектов. Замечание к тесту миграции закрыто дополнительным покрытием.
