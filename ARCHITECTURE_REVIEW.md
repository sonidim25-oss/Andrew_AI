# Architecture Review — Digital Life

**Reviewed:** 2026-10-13
**Scope:** Phase 0 only. This is a read-only preflight and design recommendation; no service, container, network, package, or system configuration was changed.

## Owner-approved direction update — 2026-10-13

The owner approves Letta + a trusted controller + a separate rootless agent runtime, subject to review of the implementation plan before changes. The concrete runtime proposal is **rootless Podman**: it is available in Ubuntu 24.04 repositories but is not installed. The plan uses a networkless tool container with a Unix-socket-only public egress proxy. No credentials have been imported or used.

## Recommendation

Use Letta as the persistent agent and memory layer, with a small custom trusted controller around it. Keep scheduling, lifecycle transitions, budget accounting, Telegram credentials, and model credentials outside the agent's tool environment. Give the agent tools through a narrow controller API; run shell, browser, and package activity in a separate rootless Podman sandbox with no host mounts or Docker socket. Do not deploy into the existing rootful Docker daemon or join the existing an existing production network network.

The host has no visible KVM device and `systemd-detect-virt` reports `none`, so a local VM is not presently practical. A dedicated external VM would provide a stronger boundary, but adds hosting cost and another system to manage. For the existing host, a separate unprivileged service account and rootless runtime are the best fit, subject to a Phase 1 proof that its networking can block access to host and container networks. The proposed tool container has `--network=none`; its only public web path is a validated Unix-domain egress proxy. If that proof fails, use a separate VM/host rather than weakening the boundary.

## Deployment findings

Host inventories and firewall snapshots are intentionally kept out of this public repository. Deployment decisions must use a fresh, private inventory of the target host and must not assume particular CPU, memory, network ranges, services, users, or firewall state. Preserve existing services and apply only reviewed, narrowly scoped changes.

## Letta and model compatibility

The current Letta docs describe a self-hosted App Server, recommend its Agent SDK for application integrations, and support external tools through callbacks to the controller. The docs list `openrouter` as a provider. The Postgres guide requires `pgvector` when using an external Postgres backend. These facts make Letta plausible, but not yet proven with the exact models and version we would pin. Keep the API server private, authenticate any non-loopback listener, persist its database, and keep model credentials in the controller/gateway rather than in the tool worker.

The original design compared several model candidates; verify current model availability and pricing during deployment. OpenRouter currently lists it at $0.15/M input and $0.47/M output tokens, with a 1M context window, 131K maximum output, and function calling. Letta currently lists `openrouter` as a model provider. Confirm end-to-end tool calls and state continuity with the pinned Letta release before final selection. Gemini comparison candidate a current Gemini Flash-family model currently lists $0.25/M input and $1.50/M output, 1M context, and function calling. Prices and model listings are point-in-time snapshots and must be checked again at setup. [the preferred initial model candidate](https://openrouter.ai/qwen/qwen3.8-flash), [Gemini 3.1 Flash Lite](https://openrouter.ai/google/gemini-3.1-flash-lite), [Letta model providers](https://docs.letta.com/api/python/resources/models).

At the current the preferred initial model candidate listing, a request containing 10,000 input tokens and 1,000 output tokens costs approximately $0.00197; about 152 such calls reach the $0.30 daily target. A 25,000-input/3,000-output request costs about $0.00516; about 58 reach that target. This suggests 100–150 cycles/day can fit only when the average cycle uses modest context and near one request; cycles are not calls and this is not a promise. Measure actual tokens, reasoning output, retries, cache charges, and tool calls. The trusted controller should reserve the worst-case cost from bounded input/output token limits before each request, reconcile actual provider usage, use a calendar-month ledger with a $1 wrap-up reserve, and stop at the $10 hard ceiling. Never rely on Andrew's `check_budget()` response to enforce spending.

Budget limits, model selection, timezone, and wake settings are deployment configuration. Do not commit them or any provider credentials to the public repository.

## Isolation design and residual risks

Run the **trusted controller** as a dedicated service account or separately managed service, outside the agent tool sandbox. It owns the lifecycle state machine, `systemd` daily timer integration, wake-request database, credential broker, token/cost ledger, event redaction, backups and kill switch. The Telegram token and OpenRouter API key are stored encrypted in the persistent credential vault and exposed only to the controller. The agent sees only narrow operations such as `sleep`, `wake_at`, `check_budget`, file operations inside its workspace, browser navigation, and bounded shell execution.

Run Letta as a trusted, unprivileged service that has no general shell tool and no provider key; route model requests through the budget gateway. Run shell and browser tools in a separate rootless Podman container owned by `andrew-runtime`, with `--network=none`, a read-only image, and only the dedicated workspace and one narrowly scoped Unix egress socket mounted. The egress socket only accepts HTTP(S) proxy requests and rejects loopback, private, link-local, Docker, Tailscale and cloud-metadata destinations after DNS resolution. Do not mount host home directories, website/bot paths, SSH directories, host `/run` generally, Docker sockets, or other containers' volumes. Use CPU, memory, PID, execution-time and disk limits. Chromium is the main resource uncertainty; budget 1–2 GiB RAM for a bounded browser worker during the initial trial, then adjust from measurements.

Force agent egress through an authenticated or otherwise non-bypassable proxy that rejects private, loopback, link-local, multicast, host, Docker bridge and cloud metadata destinations after DNS resolution; prevent direct DNS and direct-IP bypass. This is a required design proof, not yet verified on this host. Keep the agent runtime off an existing production network and off the default rootful bridge. Do not publish host ports; connect the trusted controller to a private service endpoint. Restrict browser profile and cookies to its own data volume. Keep social registration, outbound posting, email sending, account creation and vault access disabled in MVP.

Rootless containers still share the host kernel and do not equal a VM. A runtime escape or proxy policy gap could expose host or neighboring services. Existing production services may have privileged host access; inventory and preserve their boundaries during deployment. Phase 1 must prove an unprivileged tool worker cannot read host files, reach Docker APIs, access host listeners, or connect to existing container networks before it receives arbitrary shell/browser tools. If that proof cannot be made reliable without changing existing firewall or production settings, pause and move the runtime to a separate VM/host.

## Proposed initial resource envelope

These are conservative starting ceilings for a monitored 5–10 minute Phase 1 trial, not measured requirements:

- Letta/controller/database services together: 2 vCPU, 3 GiB RAM, 10 GiB persistent state.
- Tool/browser worker: 2 vCPU, 2 GiB RAM, 10 GiB writable workspace, 256 processes, bounded command time.
- Host-level reserve: keep at least 4 GiB available for existing services and OS; pause agent work on sustained host memory pressure or disk pressure.
- Backups: encrypted copy of controller state and agent memory; keep separate from the agent's writable workspace.

Total initial cap is approximately 4 vCPU and 5 GiB RAM, with up to 20 GiB agent storage. Tune down if existing website/bot resource use rises. Browser concurrency starts at one. The model runs remotely, so no GPU is needed.
